# Architecture

## The problem

Coding agents are good at code and weak at data. They don't know a table's grain, lineage, freshness or quirks, so they guess, or they explore: open file after file, run query after query. That's slow and burns tokens, and a wrong guess in a pipeline means wrong numbers in someone's dashboard. Teams that built production data agents found that context matters more than the model or the prompt ([OpenAI](https://openai.com/index/inside-our-in-house-data-agent/)).

This kit gives any coding agent that context cheaply and safely, plus a senior data engineer's way of working.

## Four layers

```
                Your agent: Claude Code · Codex · Cursor · Gemini CLI · Grok Build · …
                                          │
   ┌──────────────────────────────────────┼──────────────────────────────────────┐
   │ 1. Workflow skills   (this kit)       how a senior data engineer works:      │
   │                                       context → build → test → debug →       │
   │                                       optimize → review                      │
   ├──────────────────────────────────────────────────────────────────────────────┤
   │ 2. Tool skills       (vendors)        how a specific tool works:             │
   │                                       dbt Labs, Astronomer, …                │
   ├──────────────────────────────────────────────────────────────────────────────┤
   │ 3. Context layer     (your repo)      datawright: a compiled index of datasets,    │
   │                                       lineage, columns and readers, plus     │
   │                                       small curated notes; CLI or MCP server │
   ├──────────────────────────────────────────────────────────────────────────────┤
   │ 4. Connections       (read-only)      MCP servers or CLIs for warehouse,     │
   │                                       orchestrator, catalog, ingestion       │
   └──────────────────────────────────────────────────────────────────────────────┘
```

| Layer | Lives in | Maintained by |
|---|---|---|
| Workflow skills | `skills/` in this repo | This project |
| Tool skills | The vendors' repos, installed by `setup-data-project` when it detects the tool | Vendors |
| Context layer | `.data-context/` in your repo | Generated by `datawright build`; notes by your team and agents, reviewed in PRs |
| Connections | Each agent's MCP config, or an installed CLI | You |

## The context layer: compile, curate, query, expire

Most of what an agent needs to know about data can be worked out mechanically. Only a small part needs judgment. So the context layer splits them:

| | Derived facts | Curated knowledge |
|---|---|---|
| What | Datasets, columns, table and column lineage, producer file and line, the Airflow DAG, task and schedule that run it, readers, change history, warehouse schema, query-log usage | Grain, keys, meaning, owners, gotchas, corrections, business terms |
| Made by | `datawright build`: a SQL parser (sqlglot; dialect taken from what the repo declares, such as its dbt adapter or `.hql` files, and checked by parsing) over the repo's SQL; SQL inside Python, with constants, f-strings, `+` and `.format()` resolved; dbt manifests; Airflow DAGs and tasks, including ones built in loops; Kafka topics as datasets, through Flink SQL connector tables, Java and Scala Flink and Spark jobs, Spark Structured Streaming and StarRocks Routine Load, across several repos; Spark table and JDBC calls; and optional warehouse and catalog exports (OpenLineage, DataHub, OpenMetadata) | Agents and humans, with `datawright set` and `datawright note` |
| Stored as | `.data-context/index.db` (SQLite, gitignored, rebuilt in seconds) | `.data-context/notes/<dataset>.yml`, `glossary.yml` (small, committed, reviewed) |
| Model tokens | Zero | Only for what can't be derived |

Four rules keep it fast and keep it from turning into a pile of Markdown:

1. **Compile, don't explore.** Lineage and schema come from parsing, not from an agent reading files. Bulk warehouse metadata goes from the engine's CLI straight into files that the build reads, so it never passes through the model.
2. **Curate only what can't be derived, and only once verified.** Notes hold judgment only, as structured entries tied to a dataset and column, with a date and kind (`correction`, `gotcha`, `caveat`, `decision`). They grow where work happens, not everywhere. Agents record only what they checked in code, data or with a person: in testing, a model with no way to read the code filled in an owner it made up, and a guess stored as a note misleads every agent after it.
3. **Query, don't read.** Agents ask for a `card` (one screen, ranked, cut to a token budget, with pointers to drill down) or a `lineage` tree. The cost added to every session stays the same three lines in `AGENTS.md`, however large the index or the notes get. Agents without a shell get the same lookups as MCP tools from `datawright serve`, plus `code` to read the producing statement, and the server rebuilds the index itself when a commit is newer. Clients that load every tool definition up front pay about 1,000 tokens a session for them (Claude Code loads them on demand), so agents with a shell use the CLI.
4. **Expire, don't rot.** At each build, a note is flagged stale when the code that produces its dataset changed after the note was written, and orphaned when the dataset disappears. `lint` lists them, together with the most-used datasets that still have no recorded grain, so upkeep goes where it matters.

How it maps onto the six context layers OpenAI describes for its in-house data agent:

| OpenAI layer | Here |
|---|---|
| Table usage (schema, lineage, query history) | Compiled by `datawright build` from code, query logs, native lineage and lineage tools |
| Human annotations | `datawright set` / `datawright note`, reviewed in pull requests |
| Code enrichment | The parser reads the producing code; an agent reads one producer file only when a card is blank |
| Institutional knowledge | Links from `AGENTS.md`, the glossary |
| Memory | Notes, with staleness tracking |
| Runtime context | Live read-only queries through the connections or `datawright query` |

## Fitting any stack

Nothing in the kit assumes a particular company's setup. Each stack-specific need has an extension point, so a team adapts the kit by adding files, not by editing it:

| Need | Extension point |
|---|---|
| A format or framework datawright doesn't read (in-house DAG factory, jobs in YAML, another orchestrator, hand-written lineage) | A connector: a Python file in `.data-context/connectors/` that returns SQL, edges, producers, readers, columns or schedule links. `datawright coverage` finds the gaps; ready-made connectors live in the skill |
| Metadata only a warehouse or catalog holds (query history, native lineage, OpenLineage, DataHub, OpenMetadata) | Exports into `.data-context/imports/` |
| BI dashboards kept in the tool (Superset, Metabase) | `assets/bi_export.py` writes them into `.data-context/imports/`; a connector reads them |
| Values set at deploy time (topic and table names in environment variables) | Deploy files under `repos:`, `env:` in `config.yml`, or connector `env` records |
| Running queries on any engine | `query_command`: the engine's own CLI |
| Pipelines spread over several repos | `repos:` in `config.yml` |
| Connections to the team's tools | The connections catalog in `setup-data-project` |
| CI and trackers | Templates for GitLab and GitHub; Jira, Linear or GitHub Issues through their MCP servers or CLIs |

## Measuring it

Every `card`, `lineage` and `search` answer is logged locally (`.data-context/usage.jsonl`, gitignored). `datawright savings` turns the log into tokens, money and time saved, compared with reading the files the answer replaced. The estimate is deliberately conservative: each file counts once an hour, and grep calls, warehouse queries and context re-sent on later turns aren't counted. The price per token and seconds per file read are settings, printed with every report.

| | Real production Airflow repo | Synthetic warehouse repo |
|---|---|---|
| Size | 220 files (166 DAGs, Spark scripts, SQL), 2,500 commits | 1,500 SQL models + 300 DAG and report files |
| Build | 1.8 s, dialect auto-detected, 0 of 252 statements unparsed | 10.8 s, 0 unparsed |
| Index | 184 datasets, 96 lineage edges, 1,421 column edges, 32 readers; 163 DAGs, and 84 of 90 produced tables linked to the exact DAG task that writes them | 1,500 datasets, 2,600 lineage edges, 23,500 column edges, 500 readers |
| `card`, median | 74 tokens instead of 482 | 191 tokens instead of 554 |
| Impact query, median | (repo has shallow lineage) | 237 tokens instead of ~11,000 |
| Session of 20–27 lookups | 95% fewer tokens | 92% fewer tokens, 179 file reads avoided |

Lookups take under 10 ms. Testing on the real repo also drove fixes: auto-detecting the dialect (generic SQL parsed half the statements, the right dialect 98–100%), resolving Python constants in SQL strings, tracking every writer of a dataset, separating schema DDL from data writers, grouping 1:1 column copies on cards, and linking Airflow tasks to code through `python_callable` functions and deployed paths (`/opt/airflow/...`) rather than repo paths. Indexing the Airflow repo together with its Flink jar repo linked 53 Kafka-fed StarRocks tables to the Java job and the DAG task behind each. That took evaluating `String.format` templates, following constants across classes to `System.getenv`, and naming topics after their environment variable when the value is only set at deploy time. It also exposed two bugs, both fixed and tested: semicolons inside strings (Kafka JAAS configs) split statements, and tokenizer errors quoted SQL into the error list.

| Repo | Out of the box | After coverage and connectors |
|---|---|---|

The kit hasn't yet been measured on real tasks end to end. [ADE-bench](https://www.getdbt.com/blog/ade-bench-dbt-data-benchmarking) (open source, dbt tasks) is the next step.

## Design principles

1. **Deterministic before generative.** Anything a parser or a system table can produce, they produce. The model spends tokens only on judgment.
2. **Context over prompts.** OpenAI found that annotated tables and consistent conventions mattered more than the agent itself, and that high-level goals with good context beat step-by-step scripts. So each skill states the goal, the pitfalls and what "done" means.
3. **Few tools, few skills.** OpenAI's agent picked the wrong tool when connected to ~40; capping it at ~13 fixed that. So the kit is 11 skills and one CLI, and setup connects only what the task needs.
4. **Read-only by construction.** An agent with private data, untrusted content and a way to send data out can be steered by injected text: the "lethal trifecta" ([Simon Willison](https://simonwillison.net/2025/Jul/06/supabase-mcp-lethal-trifecta/)). So: a read-only user on non-production first, the server's read-only setting second, blocked write tools third. `datawright query` adds a guard in code: it parses each request, runs only a single SELECT, and sends the parsed tree back out as SQL with comments dropped and a row cap, so nothing hidden rides along. A SELECT that calls a side-effecting function still passes, which is why the read-only user stays first. Query results, logs and notes are data, never instructions. Query logs stay out of git, and `datawright` never prints SQL text: parser warnings are silenced and parse errors are stored without SQL snippets, because SQL in repos can contain credentials.
5. **Standards over vendors.** Only `SKILL.md` ([Agent Skills](https://agentskills.io/specification)), `AGENTS.md`, MCP, and one Python file that runs as a CLI for agents with a shell and as an MCP server for any MCP client.
6. **Connect, don't absorb.** Where a good tool exists (Astronomer's Airflow agents, dbt's MCP server, OpenLineage, a catalog), the kit connects to it through MCP, imports or a connector, and borrows ideas from the rest. It builds only the missing layer: one compiled context across the stack, and a data engineer's way of working. Copying other tools' features would mean chasing every vendor's releases.
7. **Delegate tool mechanics.** dbt Labs ([dbt-agent-skills](https://docs.getdbt.com/blog/dbt-agent-skills)) and Astronomer ([agents](https://github.com/astronomer/agents)) maintain official skills, so setup installs theirs instead of duplicating them.
8. **Progressive disclosure.** Agents load skill descriptions up front, the `SKILL.md` body when a skill triggers, and `references/`, `assets/` and `scripts/` files only when needed. Each skill folder is self-contained, because installers copy skill folders one by one.

## Repo layout

```
.claude-plugin/marketplace.json            Claude Code plugin, pointing at skills/
skills/<name>/SKILL.md                     one folder per skill (name = folder name)
skills/data-context/scripts/datawright.py        the context compiler, CLI and MCP server, copied into each repo
skills/<name>/references/, assets/         catalogs and templates, loaded on demand (CI templates in setup-data-project/assets/ci)
examples/shop/                             demo warehouse with planted bugs, to try the kit on
tests/                                     self-checks: uv run tests/test_datawright.py (also test_demo.py, test_streaming.py)
```

## Contributing

- **A connection**: add a row to `skills/setup-data-project/references/connections.md` with the publisher, run command, auth, read-only setting and a source link, checked against the server's README.
- **A warehouse export**: add the engine to `skills/data-context/references/warehouse-export.md`, with a CLI command that writes a file.
- **Parser coverage**: a failing statement from `datawright lint` plus a fix in `datawright.py`, with a case in `tests/test_datawright.py`.
- **A checklist item**: from a real incident, in the skill it belongs to. One line if possible.
- **A new skill**: only for a task data engineers repeat that no existing skill or vendor skill covers. Keep it under ~100 lines, and add it to `marketplace.json`.
